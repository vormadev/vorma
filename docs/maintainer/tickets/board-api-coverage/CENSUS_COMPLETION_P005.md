## Findings ledger updates

New findings this packet, appended to `PRESSURE_TEST_CENSUS.md`:

- F-19 (census-accuracy correction): F1's "cursor/page pagination" language and F15's
  "`replace` (-> F15 post-login)" line both described features that never existed in
  current code (page-only pagination; no post-login navigate call). Corrected in place in
  the census rows themselves rather than left to silently mislead a future reader — this
  is not a code gap, it is the census's own text drifting from the app it describes.
- F-20 (census-accuracy correction): F16's "`TaskOverrides::replace` gets a
  failure-injection test in F16" line is stale after F17 ruled `TaskOverrides` coverage
  out of Board and into `crates/vorma/tests/in_memory_test_app.rs`. The F16 bullet was
  never updated to match. Corrected in place.
- F-21 PAPERCUT (found, not fixed): `DocumentAttributes::known_safe_attribute`/
  `boolean_attribute` have no Board call site and no `public_api.rs` call site. Every
  attempt during this audit to find a non-contrived real-app use for a boolean or
  trusted-unescaped attribute on the root `<html>`/`<body>` element came up empty —
  forcing one (e.g. an invented `data-board` boolean flag with no functional purpose)
  would violate the board contract's own rule against contrived coverage ("the example
  code must say that plainly in user-facing terms and explain when an application would
  use that API" — a fabricated flag cannot honestly explain that). Recommendation: either
  find a genuine real-world document-root boolean/known-safe attribute need (revisit when
  one surfaces in a later feature) or fold this into `public_api.rs`'s existing
  `root_document_helpers_are_usable_externally` test
  (crates/vorma/tests/public_api.rs:24-35) as a type-usability check, matching how
  `HeadBuilder`'s low-level defs are handled in `root_head_helpers_are_usable_externally`
  right above it — that test already asserts usability rather than app-realism for exactly
  this class of low-level builder method, which is the more honest home for a method that
  is genuinely plumbing-shaped and does not have a natural top-level document
  boolean-attribute story. Not fixed in this packet: `public_api.rs` is a framework-owned
  test file, and touching it is a judgment call beyond "small mechanical gap that follows
  existing board patterns" — flagged for maintainer decision rather than actioned
  silently.
- F-22 PAPERCUT (found, not fixed):
  `FormData::{fields, fields_named, texts, file, files, files_named, into_body}` — board's
  actual submit flow only ever needs `text(name)` (title/url/body) and `file(name)`
  (single optional attachment), so
  `fields()`/`fields_named()`/`texts()`/`files()`/`files_named()` (the multi-value/grouped
  accessors) and `FormFile::into_body` (owned-body extraction, vs. the `body()` borrow
  board already uses at `resources.rs:166`) have no honest call site in the current
  single-attachment submit form. A second, real use would need a genuinely multi-file or
  multi-value form field in board's product surface (e.g. multiple attachments per story),
  which is a feature-shaped addition beyond "small mechanical gap," not a same-pattern
  extension of existing code. Recommendation: revisit if/when a future packet adds
  multi-attachment support; until then this is accurately described as a real but narrow
  gap, not silently absorbed.
