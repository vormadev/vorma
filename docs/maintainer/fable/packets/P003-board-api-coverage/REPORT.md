## Decisions made

- **Session note:** the executor session crashed on a transient API error (529) before
  this report was written; the harness rollback threatened uncommitted tracked-file edits.
  On resume every code/docs edit was re-inventoried on disk file-by-file and found intact
  — `git diff` (worktree vs index) is empty and `git diff --cached --stat` shows exactly
  this packet's changes plus the orchestrator's doc repairs — so nothing was re-applied
  blind. STATE.md/LEARNINGS.md/ROADMAP.md were repaired by the orchestrator and
  deliberately not touched by this packet. Post-crash re-runs of the gate commands were
  blocked by a harness-side classifier outage (see Gate results); the code tree is
  byte-identical to the tree that passed the full pre-crash verification.

- **Inventory scope = the authoritative user-facing surface**, not the raw `pub`-item scan
  in `api_inventory_rust.txt`. Per the census, that raw file includes internal
  cross-module `pub` items; the real user API is the `lib.rs` re-export map + `app!`
  emissions + `testing`/`middleware`/`tasks` + `vorma_build::run` + `TsGen`. Reconciled
  member-by-member (types AND their methods), because the census's own F-6 warns the first
  census missed nested members. Method: documented and reproducible (in the artifact);
  permanent xtask tooling is the separate `api-inventory-tooling` ticket's job, so I did
  not build it here (that would be scope creep into another ticket).

- **Implemented only genuinely uncontroversial, teaching-positive rows** that fit an
  existing Board app flow: `single_flight`, `ViewExit::with_source`,
  `HttpRequest::{method,uri,query}`, `append_header`, and the testing quartet. Each
  teaches a real app-authoring use, not a framework internal.

- **`single_flight` home = a live volatile counter** (site-activity totals in the shell
  footer). This is the honest shape for `single_flight` (coalesce concurrent duplicates,
  retain nothing) and completes the cache-policy trio in one teaching file.
  `single_flight` had zero real-world consumers repo-wide before this — only the
  `vorma-tasks` crate's own tests.

- **`extended_cache` orphan was already covered.** The packet listed an `extended_cache`
  task as a notes-example orphan needing a Board home, but current Board already has it:
  `repo::DOCS_PAGE`/`DOCS_INDEX` (`repo.rs:300-346`), a deliberately stale-tolerant TTL'd
  docs read exercised through the docs views. No new `extended_cache` demonstration was
  needed; the orphan is closed. Recorded so the packet's premise is reconciled against
  current code.

- **Escalated the standalone `vorma::tasks` runtime-lifecycle surface** rather than
  contrive Board coverage: `Tasks::{new,exec_ctx}`, `CancelToken`,
  `ExecCtx::{child,cancel_token,is_cancelled}`, `Task::id`,
  `Clock`/`SystemClock`/`ClockInstant`, `TaskOverrides`/`TaskOverrideMode`, and the
  `TaskObserver` family. An HTTP app never constructs its own `Tasks`/
  `ExecCtx`/`CancelToken` — the framework owns the runtime — so forcing these into Board
  would be contrived and (for `TaskOverrides`) reverse a prior maintainer decision to move
  that test out of Board. They are covered by `crates/vorma-tasks/tests/tasks.rs` and
  `crates/vorma/tests/public_api.rs`. This is the packet's escalation: "anything requiring
  new framework opinion or awkward fits."

- **Did NOT write framework-semantic tests in Board** (policy). The testing additions
  assert app-observable behavior (build-id header contract), not framework internals.
  `TaskOverrides` failure-injection stays in `crates/vorma/tests/in_memory_test_app.rs`
  where the maintainer already placed it.

- **Left `HttpExit::with_source`, low-level head/document type carriers, and informational
  consts as escalations/optional mechanical rows** rather than gold-plate.
  `HttpExit::with_source` is now trivially addable (same pattern as
  `ViewExit::with_source`) but was left to keep the diff focused; noted in the artifact's
  escalation table.

- **The central ruling I surface:** `crates/vorma/tests/public_api.rs` already covers much
  of the escalated type-carrier/standalone surface as a "…is_usable_externally" test. The
  literal "Board must cover 100%, period" rule conflicts with the maintainer's own
  placement of that surface in framework tests and the deliberate removal of
  `TaskOverrides` from Board. Recommendation (in the artifact + census F-17): ratify in
  `docs/maintainer/board-example/README.md` that Board covers the surface an application
  uses in a realistic app flow, while the standalone tasks runtime-lifecycle surface and
  low-level type carriers are sovereign-crate + `public_api.rs` coverage.

- **Did not run `oxfmt --write .` globally for the gate.** It reflows all markdown
  (prose-wrap) and dirtied 13 out-of-scope Fable-owned docs when tried; those were
  restored to exact HEAD content via read-only `git show` redirects (`git checkout` is a
  forbidden git write). Scoped writes were used for my own files and `--check` for
  verification. See F-18 and the escalation below.

   `TasksOptions.observer`. If the literal 100%-in-Board rule stands, this is worth a

   "app-flow" reading is adopted, it is optional.

3. **`ts-fmt` gate friction (F-18) — the honest caveat for a strictly-green aggregate
   `make ts-gate`.** `make ts-fmt` is `oxfmt --write .`, which prose-wraps ALL markdown;
   at the time of this packet's work the maintainer docs under `docs/maintainer/` had
   drifted from oxfmt's config, so `make ts-fmt-check` (and thus the aggregate `ts-gate`)
   was red on 13 out-of-scope Fable-owned files independent of this packet. I did not
   normalize them: rewriting Fable-owned protocol/state files is out of scope for a Board
   packet. My own files (Board + my two docs artifacts) are fmt-clean. Decision needed:
   either a Fable-owned housekeeping pass to normalize the docs through oxfmt, or exclude
   `docs/maintainer/**` from oxfmt if hand-maintained process docs are intentionally not
   machine-prose-wrapped. (The orchestrator has since repaired STATE/LEARNINGS/ROADMAP;
   the aggregate re-run at review will show the then-current drift set.)
