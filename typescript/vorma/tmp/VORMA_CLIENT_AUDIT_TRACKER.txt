Vorma Client Audit Tracker (Declarative, Resume-Safe)

Purpose

- This document is the canonical, current-state tracker for the comprehensive
  Vorma browser-client behavioral audit and regression comparison.
- It is explicitly designed so work can resume without relying on chat history.

Non-Negotiable Analysis Method

- Perform first-principles source analysis by reading implementation files
  directly.
- Do not treat test execution as the primary discovery mechanism.
- Do not treat pattern-grep/search hits as evidence of behavior by themselves.
- Every recorded behavior must be justified from direct code reading and
  control-flow reasoning.
- For each behavior, answer:
    1. What observable behavior occurs?
    2. Under what conditions?
    3. What user interest does this protect?
    4. What would break if this behavior changed?

Explicit Clarification Captured

- This audit should NOT be run as a command-heavy process.
- The intended workflow is direct file reading and careful reasoning, not
  running tests and not grep-led pattern hunting.

- Permanent normative spec:

- Permanent normative-spec test coverage traceability map:
    - typescript/vorma/spec/client-normative-test-coverage.md
- Temporary branch-comparison report (disposable before merge):

- High-level coverage checkpoint:

Audit Scope Definition

- In scope: all TypeScript shipped to browsers that is part of, or directly
  participates in, Vorma framework client behavior.
- Includes: client runtime, navigation/prefetch/redirect/loader behavior,
  abort/cancel semantics, race handling, adapter-integrated client behavior.
- Excludes: server-only code paths and non-browser runtime behavior.
- Excludes explicitly: `create` and `vite`.

Regression Definition

- Regression = an observable user story/behavior that worked on main and no
  longer works on current branch, assuming application code is migrated
  correctly to current APIs.
- API signature changes alone are not regressions.

Baseline Bug Filter Rule

- Baseline (`main`) behavior is evidence for intended semantics, not automatic
  normative truth.
- Clearly incorrect or footgun behavior in baseline shall be treated as a
  baseline defect and shall not be enshrined in the normative spec.
- Branch comparison shall evaluate current behavior against normative intent,
  not against baseline defects.

Specification Authoring Rules

- Normative spec entries must be implementation-backed and observable.
- Each entry must include:
    - Stable Spec ID (for cross-branch mapping)
    - User story statement
    - Trigger conditions
    - Expected observable behavior
    - Protected user interest
    - Notes on cancellation/ordering/race constraints where relevant
- Avoid historical narration; keep statements in present-tense normative form.

Documentation Declarative Discipline

- The tracker, high-level topic map, normative spec, and temporary regression
  report shall remain strictly declarative and present-tense.
- Prohibited content includes historical timelines, backward-looking narration,
  conversational commentary, and changelog-style accumulation.
- Progress shall be represented by updating current-state fields in place, not
  by appending historical logs.
- Superseded statements shall be replaced or removed, not preserved as document
  history.

UI Adapter Spec Normalization Rule

- Do not create separate full behavior sections per framework adapter
  (React/Preact/Solid/etc.).
- State adapter behavior once in generic form as framework-agnostic adapter
  contracts.
- Clarify that observable behavior and usage patterns are expected to be
  equivalent across all current and future UI adapters.
- Differences are only acceptable when they do not change user-observable
  semantics.

Comparison Rules

- Compare behavior by spec ID and explicit behavior statements, not by API
  naming.
- A changed implementation is acceptable if the same user story still holds.
- Record only true behavior regressions in temporary report.

Execution Plan

- Step 1: Create/maintain `typescript/vorma/spec/client-normative-spec.md` as
  the permanent authoritative spec.
- Step 2: Use `typescript/vorma/tmp/client-high-level-topic-map.md`
  (`HL-01`..`HL-26`) as the mandatory topic index and sectioning backbone.
- Step 3: Extract baseline behavior from `main` first, line-by-line, and encode
  each requirement with stable IDs.
- Step 4: Required extraction order:
    - bootstrap/state
    - navigation/fetch/skip/redirect/submission
    - links/prefetch/history/scroll/events/head
    - adapter-generic contracts
- Step 5: For each requirement ID, record:
    - user story
    - trigger conditions
    - expected observable behavior
    - protected user interest
    - cancellation/ordering/race constraints when applicable
- Step 6: Map current-branch behavior to the same requirement IDs and classify
  only as:
    - preserved behavior
    - changed implementation with preserved semantics
    - regression (behavior no longer satisfies the same user story)
- Step 7: Write regressions only to
  `typescript/vorma/tmp/main-vs-current-regressions.md`.
- Step 8: Keep branch-comparison content temporary and keep normative spec
  branch-agnostic.
