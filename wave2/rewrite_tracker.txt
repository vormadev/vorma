Wave2 Rewrite Tracker
Last updated: 2026-03-05

Purpose
- Preserve declarative architectural intent and next actions so handoff can continue without re-litigating fundamentals.

Non-Negotiable Constraints
- Wave2 runtime/buildtime boundary stays strict.
- `wave2` runtime-facing package does not import `wave2/wavebuild`.
- Wave core stays framework-agnostic.
- Framework-specific behavior stays in adapters or framework-owned packages.
- Planner/execution model remains minimal: terminal goals + task graph dependencies.

Package Surfaces
- `wave2/wave.go`
  - App-facing runtime API surface.
- `wave2/wavebuild/wavebuild.go`
  - Build/dev orchestration contracts and default planner/arbiter/executor wiring.
- `wave2/wavefw/wavefw.go`
  - Framework-facing adapter registration and signal translation policy.

Canonical Planning Model
- Input reduction:
  - Raw batch -> typed facts (`BatchFacts`) -> normalized events (`EventType`) -> terminal goals (`EffectID`).
  - CSS event classes remain strictly `critical_css_source_changed` and `normal_css_source_changed`; both may co-occur, and no shared-CSS pseudo class exists.
  - Config/public/private-static semantics are provided by configuration-aware upstream metadata; Wave2 does not infer those categories from path naming conventions.
  - Default facts collection does not infer semantic event classes from project-shape path patterns.
- Policy:
  - Event rules are pure data (`EventRule` + `ConditionFacts`).
  - Arbitration is pure data (`ArbitrationRuleSet`).
- Output:
  - `ExecutionPlan` carries terminal goals only (`TerminalGoals`), not ordered step groups.
- Execution:
  - Executor fans out terminal goal task roots in one `kit/tasks` context.
  - Dependency sequencing and parallelism are owned by task dependencies, not orchestrator step ordering.

Identity/Freshness Policy
- Generation identity is explicit and typed.
- `PlannerInput`, `BatchInput`, `RawBatchInput`, and `ExecutionPlan` carry `GenerationID`.
- Framework signal freshness tokens derive from `ExecutionPlan.GenerationID`.
- Goal execution keys derive from plan mode + generation + effect id.

Checklist (Hardest First)
1) Canonical task-root dependency map
- Keep one declarative mapping from each canonical terminal goal to prerequisite ensure-goals.
- Keep dependency ownership in task graph, not planner ordering fields.
- Keep task-root dependency coverage validation available on the engine.
- Fill dependency entries only where first-principles guarantees require prerequisites.

2) Task input/output contract
- Keep plan-level data explicit in typed task inputs.
- Keep task output sharing in prerequisite task return values and `kit/tasks` result caching.
- Keep native context usage limited to cancellation/deadline and external call propagation.
- Keep this contract independent from framework-specific transport details.

3) Wave app-facing API shaping
- Finalize `wave2/wave.go` app API so developer ergonomics remain simple while delegating orchestration to `wavebuild`.
- Keep options explicit and minimize convenience cruft.

4) Framework signal/action policy tightening
- Keep `wavefw` translation declarative and minimal.
- Ensure signal/action vocabulary stays purely observable and transport-agnostic.

Do Not Do
- Do not re-introduce runtime->buildtime imports.
- Do not encode framework-specific endpoint names or file conventions in Wave2 core.
- Do not add compat/transitional wrappers.
- Do not re-introduce planner-level execution ordering layers.
