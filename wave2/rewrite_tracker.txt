Wave2 Rewrite Tracker
Last updated: 2026-03-06

Purpose
- Preserve a declarative, forward-looking architecture plan so handoff stays aligned without re-litigating fundamentals.

Non-Negotiable Constraints
- Wave2 runtime/buildtime boundary stays strict.
- `wave2` runtime-facing package does not import `wave2/wavebuild`.
- Wave core stays framework-agnostic.
- Framework-specific behavior stays in framework-owned adapters/packages.
- Execution model is phased:
- `events -> build -> backend_settling -> frontend_settling`.
- Each phase selects terminal goals, then executes those roots in `kit/tasks`.
- Phase boundaries enforce cross-phase ordering.
- Inside each phase, sequencing and parallelism are owned only by `kit/tasks` task dependencies.
- Do not introduce a second DAG/topological scheduler outside `kit/tasks`.
- Four-phase orchestration stays function-based (`RunFourPhasePipeline`) with no runner-interface/config wrapper layer.
- Default to direct calls. Do not add wrappers, convenience helpers, or "ergonomic" adapter layers unless there is explicit, repeated evidence that direct-call usage is too painful or confusing.

Package Surfaces
- `wave2/wave.go`
  - App-facing runtime API surface.
- `wave2/wavebuild/wavebuild.go`
  - Build/dev phase contracts and phased-pipeline orchestration contract.
- `wave2/wavefw/wavefw.go`
  - Framework-facing signal translation policy.

Canonical Batch Pipeline
- Phase 1: Events
- Raw watcher batch is reduced to typed facts and normalized event categories.
- CHMOD policy remains explicit in event classification (empty-file CHMOD can be actionable; non-empty CHMOD-only noise is suppressible).
- Phase 2: Build
- Planner reduces phase-1 output to build terminal goals.
- Build roots run in `kit/tasks` and declare prerequisites by calling prerequisite tasks.
- Pipeline composition calls phase root tasks directly; no one-line `RunPhase*TaskGraph` wrappers.
- Phase 3: Backend Settling
- Planner reduces phase-2 outcomes to backend-settling terminal goals.
- Backend settling covers process/framework readiness concerns.
- App/Vite readiness waiting remains one backend-readiness terminal goal, not separate phase-goal flags.
- Phase 4: Frontend Settling
- Planner reduces phase-3 outcomes to browser-settling terminal goals.
- Frontend settling covers CSS hot updates, notify-Vite-public-filemap-changed, revalidate, hard reload, or no browser action.

Parity-Critical Observable Goals
- Batches that contain only editor/lock/churn noise produce no rebuild, restart, framework refresh, or browser refresh.
- Real content edits are never dropped, including editor edge cases where empty-content transitions surface as CHMOD-like event shapes.
- Generated output changes never create self-triggered rebuild/reload loops.
- No-op config saves (including path-alias and atomic-save shapes) produce no visible action; semantic config changes produce one coherent config-restart cycle.
- CSS source changes refresh styles without full document reload when safe.
- Public static changes update served asset mappings and canonical public file map, including removal of stale mappings, and propagate the update to active dev runtime/browser state.
- Private static, route-definition, and template changes converge to coherent new output state without mixed-generation responses.
- App-defined watch behavior can request explicit outcomes (restart, recompile, revalidate, notify-Vite-public-filemap-changed, hard reload, framework refresh), and the batch resolves them deterministically.
- During build-failure/retry windows, user-visible behavior remains stable and resumes cleanly after a valid fix.
- Stale deferred reload attempts are rejected instead of mutating newer runtime state.
- Dev-only reload routes are unavailable in prod and enforce endpoint method contracts.
- Concurrent request/reload traffic never serves mixed old/new build artifact sets in a single response.
- Dev/prod integration behavior remains stable across supported UI adapters.

Task Context Contract
- One batch-scoped `tasks.Ctx` is shared across all executed phases in a batch.
- Pipeline orchestration stays direct and sequential over phase root tasks; do not add wrapper orchestration tasks around phase calls.
- Native `context.Context` provides cancellation/deadline and is wrapped exactly once per batch.
- Task identity and output reuse are owned by `kit/tasks`; phase planners do not duplicate that logic.
- Phase task input keys stay comparable for `kit/tasks` identity semantics.
- Batch input stays comparable by carrying non-comparable event/execution payloads through pointers in phase-input envelopes.
- Batch execution scope carries a required `PhaseEffectExecutor` for terminal side effects.
- Events batch inputs are assembled directly with explicit execution scope.
- Visibility stays out of core phase contracts: use plain runtime logging, and use stable `__WAVE_INTERNAL_TEST_MODE=1` task-name logging with early-return for task-selection tests.

Framework Signal Contract
- Framework signal vocabulary stays observable and transport-agnostic.
- Signal payload shape remains stable:
- `type`, `freshness_token`, `trigger`, `metadata`.
- Signal translation remains framework-owned in `wave2/wavefw`.

Checklist (Hardest First)
1) Define final phase-1 event/fact schema
- Lock the minimal event/fact model required to decide observable outcomes deterministically.
- Ensure the model can represent noise-only batches, semantic config changes, and actionable content edits.
- Keep `ObservedBatchEvent` classification-minimal: event type plus semantic noise/no-op flags only.
- Keep phase-1 boundary directly on `EventsPhaseInput` -> `EventsPhaseFacts` with no scenario-shaped external input.
- Keep `EventsPhaseFacts` planner-minimal: `mode`, `generation_id`, deduped `event_types`, reduced app-request outcomes, and retry flag only.
- Keep phase-1 task graph thin: one facts reduction task feeding the phase-1 planner, with no pass-through envelope/normalize tasks.

2) Define final phase planners as pure reductions
- Keep planners pure and deterministic.
- Keep planner output as terminal goals only (per phase).
- Encode build-retry gating and browser action precedence as explicit planner policy: `hard_reload > notify_vite_public_filemap_changed > revalidate > css_hot_reload > none`.
- Frontend-settling goal surface stays single-action (`terminal_browser_action`) rather than multi-boolean action flags.
- Browser action remains single-value from phase-1 goals through phase-2 backend goals to phase-3 frontend goals; do not fan out into per-action booleans between phases.
- Keep each phase planner backed by one pure reduction helper over prior-phase facts/goals.
- Keep mode policy explicit at the pipeline boundary: `dev` runs all four phases; `prod` bypasses phases 1/3/4 and runs phase 2 only.
- Keep phase-2 backend-settling planner output empty in `prod` because backend/frontend settling phases are skipped.
- Keep phase 2/3/4 task graphs thin: avoid no-op `Ensure*`/`Root*` wrappers and execute terminal effects from direct task roots.
- Keep per-phase single-effect task declarations generated by one tiny constructor helper to avoid repetitive wrapper bodies.
- Keep phase 4 aligned with phases 1-3 by exposing one direct phase-root task (`Phase4ExecuteTerminalBrowserActionTask`) rather than a pass-through phase function wrapper.

3) Define final app-requested action reduction model
- Preserve deterministic reduction when app-defined watch behavior requests outcomes that overlap or conflict with implicit file-driven outcomes.
- Keep app-requested browser intent as one explicit `requested_terminal_browser_action` value and merge it with implicit browser intent through one explicit precedence policy.
- Keep app-defined watch event classes free of heuristic default side effects; concrete terminal goals come from reduced facts/outcomes only.
- Keep `notify_vite_public_filemap_changed` as a browser-action category with explicit precedence, but do not treat hard reload as a healing fallback when notify fails.
- Keep notify-failure recovery explicit and healing-first: if notify fails for current generation, cycle/restart Vite, wait ready, then hard reload.

4) Define final static-processing policy
- Preserve canonical public-filemap correctness and stale-output cleanup.
- Preserve minimal-work execution decisions while keeping output correctness unchanged.
- Keep stale-public-static cleanup and public-filemap regeneration as explicit, separate build goals.
- Keep browser notify-Vite planning derived from phase-2 public-filemap artifact outcome facts, not directly from raw event categories.

5) Define final framework-facing phase boundaries
- Keep Wave2 phase outputs framework-agnostic.
- Keep framework-owned translation and transport in `wavefw` or framework packages.
- Preserve stale-guarded deferred runtime refresh behavior through stable generation/freshness identity fields.
- Keep framework-signal reduction as a pure Wave2 reduction from backend-settling goals.
- Keep framework signals emitted only for dev runs that execute backend/frontend settling phases.

6) Keep phase contract names production-neutral
- Keep phase contract symbols and comments free of temporary naming.

7) Replace placeholder task bodies with real side effects incrementally
- Keep task graph topology stable while replacing placeholder bodies.
- Preserve idempotent ensure-style task semantics.
- Route terminal phase tasks through a single `PhaseEffectExecutor` contract keyed by explicit `PhaseEffectID` values.

Do Not Do
- Do not re-introduce runtime->buildtime imports.
- Do not encode framework-specific endpoint names or file conventions in Wave2 core.
- Do not add compat/transitional wrappers.
- Do not add planner-level dependency graphs that duplicate `kit/tasks`.
- Do not add external DAG/topological execution engines.
- Do not add dedicated observability/debug plumbing (snapshot/trace/recorder APIs) to Wave2 core contracts.
